Este documento detalla el diseño de software y la infraestructura del sistema Cocktrail.

---

## 1. Visión General

La arquitectura V2 de Cocktrail reestructura el monolito original en un **monorrepo con separación física y lógica** entre el frontend, el backend y los tipos compartidos de dominio.

```
Cocktrail/                         (monorepo root)
├── packages/
│   └── shared/                    @cocktrail/shared — tipos de dominio
├── apps/
│   ├── api/                       cocktrail-api — Express + TypeScript
│   ├── web/                       cocktrail-web — Next.js (frontend only)
│   └── docs/                      cocktrail-docs — Sitio de Documentación (Fumadocs)
├── pnpm-workspace.yaml
└── ARCHITECTURE_V2.md             (documento raíz original)
```

### Motivación de la V2

| Problema (V1) | Solución (V2) | Razón Técnica |
| :--- | :--- | :--- |
| Estado in-memory acoplado en `globalThis` | **Repository Pattern** | Permite inyectar repositorios InMemory o Supabase (Fase 5) sin tocar lógica de negocio. |
| Frontend importa directamente del server | **Capa de Servicios HTTP (`api-client.ts`)** | Aísla la API del renderizado e implementa re-intentos y control de fallos. |
| APIs de lectura sin autenticación | **Auth Middleware por rol** | Restringe acceso a datos sensibles (ventas, eventos) a perfiles específicos. |
| Claves criptográficas en código (hardcoded) | **Zod Env Validation (Fail-fast)** | Previene despliegues inseguros interrumpiendo el booteo si faltan variables. |
| Despliegue único | **Despliegues Dedicados** | Frontend estático en Vercel (Edge) y API robusta en servidor Railway. |

## 2. Paquete Compartido — `@cocktrail/shared`

Contiene todos los tipos de dominio y esquemas que utilizan tanto el frontend como el backend. Su objetivo es asegurar un **único punto de verdad** para las estructuras de datos.

*   **Ubicación:** `packages/shared/src/domain.ts`
*   **Consumo:** Importado localmente mediante la directiva `workspace:*` de pnpm.
*   **Contenidos:**
    *   Definiciones de roles (`Role`: Admin, Caja, Barra) y estados de orden (`OrderStatus`).
    *   Tipos de negocio: `Drink`, `OrderItem`, `Order`, `PaymentMethod`.
    *   Estructuras analíticas: `CashSale`, `NightEvent`, `EventSummary`, `EventTotals`.
    *   Modelos de entrada (`NewOrderInput`, `NewCashSaleInput`).

## 3. Backend — `apps/api`

El backend está diseñado como un servidor de APIs e inyección de eventos estructurado en tres capas independientes.

```
Request ──> Controller (HTTP / Zod) ──> Service (Business Logic) ──> Repository (Data / DB)
                                                                 └── SSE Manager (Real-time Broadcast)
```

### 3.1 Módulos del Servidor

| Módulo | Descripción | Rutas HTTP | Repositorio |
| :--- | :--- | :--- | :--- |
| **`auth`** | Manejo de sesión y autenticación segura con JWT/Cookies | `POST /login`, `POST /logout`, `GET /me` | — |
| **`drinks`** | CRUD y disponibilidad de bebidas en el menú | `GET /api/drinks` | `DrinksRepository` |
| **`orders`** | Procesamiento de pedidos e historial general | `POST /orders`, `PATCH /orders/:id`, `GET /orders/active` | `OrdersRepository` |
| **`cash-sales`**| Registro y cuadre de caja manual | `POST /cash-sales`, `GET /cash-sales` | `CashSalesRepository` |
| **`events`** | Control de estado de noche, temáticas y cierre | `GET /events/state`, `POST /events/close` | — |
| **`sse`** | Canal de transmisión unidireccional en tiempo real | `GET /api/events` | — |
| **`tickets`** | Canje seguro y descentralizado de tickets QR | `POST /api/tickets/redeem` | `TicketsRepository` |

### 3.2 Patrón Repositorio (Repository Pattern)

Para permitir una transición transparente entre entornos, la lógica de negocio no interactúa directamente con la persistencia. En su lugar, se comunica a través de interfaces TypeScript estrictas:

```typescript
export interface OrdersRepository {
  create(order: Order): Order;
  findById(id: string): Order | undefined;
  findByToken(token: string): Order | undefined;
  findActive(): Order[];
  list(): Order[];
  updateStatus(id: string, status: OrderStatus): Order;
  clear(): void;
}
```

*   **Desarrollo / Testing (Fase 1-3):** `InMemoryOrdersRepository` respaldado por colecciones `Map` de JS.
*   **Producción / Persistencia (Fase 5):** `SupabaseOrdersRepository` conectado a PostgreSQL.

## 4. Seguridad (Security by Design)

El backend incorpora medidas robustas contra vectores de ataque comunes descritos en OWASP Top 10:

*   **Helmet:** Configura cabeceras HTTP de seguridad para evitar Clickjacking y Cross-Site Scripting (XSS).
*   **CORS Whitelist:** Restringe peticiones con credenciales únicamente desde la URL del frontend (`env.FRONTEND_URL`).
*   **Rate Limiting:**
    *   `generalLimiter`: Máximo 100 peticiones por 15 minutos por IP.
    *   `loginLimiter`: Máximo 5 intentos de inicio de sesión por 15 minutos (mitiga ataques de fuerza bruta).
    *   `orderLimiter`: Máximo 10 pedidos creados por minuto por dirección IP (bloquea bots de spam).
*   **Timing-Safe Equal:** El canje de firmas criptográficas utiliza `crypto.timingSafeEqual` para bloquear ataques de temporización (timing attacks).
*   **Fail-Fast Envs:** Si el servidor se inicia en producción con una variable `AUTH_SECRET` menor a 32 caracteres, el proceso se aborta inmediatamente.

## 5. Frontend — `apps/web`

La interfaz de usuario está construida sobre **Next.js 16 (App Router)** y estilizada de forma dinámica con **Tailwind CSS v4**.

### 5.1 Capa de Servicios
Toda la lógica de consumo HTTP se centraliza en `src/services/api-client.ts`. Si `NEXT_PUBLIC_API_URL` está vacío, el cliente apunta a rutas relativas para desarrollo local con proxy. Al proveer un dominio, cambia al backend externo de forma instantánea.

### 5.2 Control de Accesos mediante Middleware
El archivo `apps/web/middleware.ts` intercepta las peticiones a rutas administrativas (`/admin`) y de barra (`/barra`).
1.  Extrae la cookie `cocktrail_session`.
2.  Desencripta y verifica la firma HMAC utilizando **Web Crypto API** directamente en el Edge Runtime de Next.js.
3.  Redirige antes de servir el código HTML del cliente, evitando parpadeos de interfaz (flickering) y mejorando sustancialmente la experiencia del usuario.

## 6. Decisiones Técnicas Clave

| Decisión | Alternativa Evaluada | Justificación y Razón de Diseño |
| :--- | :--- | :--- |
| **pnpm Workspaces** | Repositorios separados | Evita duplicar código de interfaces; sincroniza tipos de negocio instantáneamente en tiempo de compilación. |
| **HMAC Local en Edge** | Fetch al backend en cada ruta | Cero latencia de red en redirecciones del middleware; validación de cookies ultrarrápida. |
| **Tickets QR Compactos** | UUIDs tradicionales de 36 caracteres | Reduce el tamaño y complejidad del código QR. Agiliza el escaneo físico en condiciones de poca luz y permite la digitación manual veloz si falla la cámara. |
| **Feedback Háptico** | Sonidos y alertas visuales clásicas | El ruido ambiente de las discotecas invalida alertas acústicas. El uso de la API de vibración de navegadores (`navigator.vibrate`) y destellos a pantalla completa aseguran que el barman reciba confirmación visual/háptica inmediata del canje. |
| **Aislamiento de Roles** | Panel único multiperfil | Impide accesos no autorizados a la caja del evento por parte de barman u operadores externos. |
